# httpgrep v1 实施计划

> 给执行代理：按 TDD（red→green）逐个行为实现。只读本计划里「公共约定」和分配给你的那一节，设计细节以 `docs/superpowers/specs/2026-09-28-httpgrep-design.md` 为准，术语以 `CONTEXT.md` 为准。

状态：执行中
日期：2026-09-28

目标：实现设计文档描述的 httpgrep v1。

架构：一条单线程流水线。pcap 读记录，decode 解出 TCP 段，tcp 重组字节流，http1 切出消息，engine 配对交互、管理超时和内存，match 判断命中，output 渲染输出块。`--cpus N` 时按连接分给 N 个 engine 实例。

技术栈：Go 1.27，只用标准库；测试只用 `testing`。

## 1. 执行方式

用 workflow 编排子代理，分 5 个阶段。每个阶段结束后，父会话检查磁盘上的实际产物（git log、`go test ./...`），不看子代理的返回值。

| 阶段 | 内容 | 并行度 | 工作目录 |
|---|---|---|---|
| 0 | 仓库骨架（本节第 4 部分） | 父会话自己做 | 仓库根 |
| 1 | 8 个独立包 L1–L8 | 8 条并行通道 | 每条通道一个 git worktree |
| 2 | `internal/engine` | 1 | 仓库根 |
| 3 | `cmd/httpgrep` 与多核分发 | 1 | 仓库根 |
| 4 | 真实样本与平台验证 | 1 | 仓库根 |
| 5 | 整体评审和修复 | 2 个评审并行，1 个修复 | 仓库根 |

每条通道的流程是：实现者 → 评审者 → 实现者修复 → 评审者复核，复核最多一次。

- 实现者按 TDD 开发，每个行为转绿后就提交一次，免得超时中断时丢掉工作。
- 评审者只读不改。它逐条对照本计划和设计文档检查，再看测试质量：是否只测接缝、期望值是否独立得出、有没有漏掉行为清单里的条目。它会运行 `go test`、`go vet` 和 `gofmt -l`。
- 修复由同一个实现者线程完成，这样它保有原来的上下文。复核后仍有阻断问题的，交给父会话处理。

模型分配：

- L3（tcp）、L4（http1）、阶段 2–5 的所有代理，以及所有评审者，用 `kiro-gateway/claude-opus-5-5`。
- 其余通道用默认模型。

阶段一的通道之间没有依赖，只共用第 4 部分的两个类型文件。每条通道只改自己的目录，合并时不会冲突。父会话事先建好 worktree 和分支：分支叫 `pi/httpgrep-<通道>`，目录是 `.worktrees/<通道>`。阶段一结束后，父会话把各分支依次 `git merge --no-ff` 进 `pi/httpgrep-v1`。

## 3. 公共约定（所有代理必读）

- 模块名是 `httpgrep`，用 Go 1.27，不引入任何第三方依赖，`go.mod` 保持不变。
- 每个行为走一轮 red → green：先写一个失败的测试并运行，确认它确实失败；再写刚好让它通过的实现。不要一次写完所有测试，也不要预先实现清单外的功能。
- 期望值要有独立来源：手算的字面量、设计文档里的样例，或者 tcpdump/tshark 的输出。不要在断言里用和实现相同的方法把期望值再算一遍。
- 测试用表驱动，文件放在包目录下（`xxx_test.go`，使用 `package xxx_test`）。测试数据由测试代码生成，不读 `~/Downloads` 里的真实抓包。
- 每次提交前运行：`gofmt -l .` 输出为空，`go vet ./...` 和 `go test ./...` 通过，本包再跑一遍 `go test -race`。
- 提交只 add 自己负责的路径，不用 `git add .`。提交信息用中文，格式是 `feat(包名): 说明`，末尾空一行写 `Co-Authored-By: Pi`。不要 push。
- 不要修改别的通道负责的目录，也不要改 `internal/pcap/types.go` 和 `internal/decode/segment.go`。发现接口定义有问题时，在最终报告里说明，不要自己改别人的包。
- 性能要求：热路径上不为每个包分配内存，传入的切片不拷贝，除非必须保留到回调之后。单核吞吐的目标是 50MB/s，按每个包 1KB 算约 5 万包/秒，所以每层的耗时都要远小于 20µs/包。
- 注释和文档用中文，标识符、错误信息和输出文本用英文。

## 5. 阶段一：8 条并行通道

### L1 `internal/pcap`：读 pcap 数据流

文件：`internal/pcap/reader.go`、`reader_test.go`。

```go
var (
	ErrEmpty   = errors.New("empty input")
	ErrPcapNG  = errors.New("pcapng is not supported; capture with tcpdump -w")
	ErrNotPcap = errors.New("input is not a pcap stream; pipe it from tcpdump -U -w -")
	ErrCorrupt = errors.New("corrupt pcap record")
)

type Reader struct{ /* 未导出 */ }

// NewReader 读取并校验 24 字节的文件头。
func NewReader(r io.Reader) (*Reader, error)
func (r *Reader) LinkType() LinkType // 文件头 network 字段的低 16 位
// Next 返回下一条记录。正常结束，或者最后一条记录不完整时，返回 io.EOF。
func (r *Reader) Next() (Packet, error)
```

行为清单：

1. 支持 4 种 magic：`a1b2c3d4`（微秒）和 `a1b23c4d`（纳秒），各有小端和大端两种写法。时间戳要精确到对应精度。
2. 开头是 `0a0d0d0a` 时返回 `ErrPcapNG`。输入为空时返回 `ErrEmpty`。不足 24 字节，或者 magic 不认识，返回 `ErrNotPcap`。
3. 最后一条记录的头或数据不完整时，前面完整的记录照常返回，之后返回 `io.EOF`。
4. caplen 大于 16 MiB 时返回 `ErrCorrupt`。origlen 小于 caplen 时，`OrigLen` 取 caplen。
5. 底层 reader 每次只给 1 个字节时（`testing/iotest.OneByteReader`），结果不变。
6. 用 1 MiB 的 `bufio.Reader`。连续调用 `Next` 时，`Data` 复用内部缓冲区，稳定状态下每条记录的分配次数是 0，用 `testing.AllocsPerRun` 断言。要有基准测试。

### L2 `internal/decode`：从链路层解码到 TCP

文件：`internal/decode/decode.go`、`decode_test.go`（不改 `segment.go`）。

```go
// Supported 判断这种链路层类型能否解码：0、1、12、14、101、108、113、276。
func Supported(link pcap.LinkType) bool
// Decode 把 data（抓到的字节）解码到 seg。origLen 是线上原始长度。
// seg.Payload 引用 data，不拷贝，也不分配内存。
func Decode(link pcap.LinkType, data []byte, origLen int, seg *Segment) Result
```

行为清单（测试里的帧由测试自己拼字节，不依赖别的通道）：

1. 以太网 + IPv4 + TCP：解出地址、端口、Seq、Ack、Flags 和 Payload。IPv4 地址满足 `Is4()`。
2. 以太网最短 60 字节，不足的部分会补填充字节。负载长度按 IPv4 总长度截取，填充字节不能算进 Payload。
3. 支持 802.1Q 和 QinQ（0x88A8 外层加 0x8100 内层）VLAN 标签。
4. SLL（113）：协议号在偏移 14，头长 16 字节。SLL2（276）：协议号在偏移 0，头长 20 字节。
5. NULL（0）：协议族 2 是 IPv4，24、28、30 是 IPv6。按大端和小端两种读法都要认。LOOP（108）：只按大端读。
6. RAW（101、12、14）：按首字节的高 4 位区分 IPv4 和 IPv6。
7. IPv4 头带选项（IHL 大于 5）、TCP 头带选项（数据偏移大于 5）时，都能正确找到负载。
8. IPv6 要跳过扩展头：逐跳选项（0）、路由（43）、目的选项（60）。遇到分片头（44）返回 `Fragment`。
9. IPv4 设了 MF 位或片偏移不为 0 时返回 `Fragment`。只设 DF 位不算分片。
10. 被 snaplen 截断时，`Missing` 等于 IP 长度字段算出的负载长度减去抓到的负载长度。
11. IPv4 总长度为 0（网卡 TSO 抓包常见）或 IPv6 负载长度为 0 时，负载长度改用 `origLen` 推算。
12. IP 头或 TCP 头不完整、长度字段比头还短时，返回 `Malformed`。UDP、ICMP、ARP 返回 `NotTCP`。
13. 用 `testing.AllocsPerRun` 断言 `Decode` 每次调用分配 0 次。要有基准测试。

### L3 `internal/tcp`：连接表和 TCP 重组

文件：`internal/tcp/assembler.go`（可按职责拆成多个文件）、`assembler_test.go`。测试直接构造 `decode.Segment`，不需要 pcap。

```go
type Side uint8 // 0：发起方（看到 SYN 时就是客户端）；1：另一方

type Key struct{ A, B netip.AddrPort } // A 是 side 0 的地址

type ConnInfo struct {
	Key        Key
	RolesKnown bool // 看到了 SYN 或 SYN-ACK，side 0 确定是客户端
	Start      time.Time
}

type CloseReason uint8

const (
	CloseFin      CloseReason = iota // 两个方向的 FIN 都已按序生效
	CloseReset                       // 收到 RST
	CloseIdle                        // 空闲超过 IdleTimeout
	CloseReplaced                    // 同一四元组上出现了新连接
	CloseEOF                         // 调用了 Flush
	CloseEvicted                     // 调用了 Release
)
```

```go
// Handler 接收一条连接的事件。回调里不得调用 Assembler 的方法。
type Handler interface {
	// Data 按序交付 side 方向的字节。off 是 b 在该方向流里的偏移，从 0 开始。
	// b 只在回调期间有效。peerAck 是这个包确认到的对端流偏移
	// （即对端流下一个期望的偏移），不知道时为 -1。
	Data(side Side, off int64, b []byte, peerAck int64, ts time.Time)
	// Gap 表示 side 方向 [off, off+n) 这段没抓到。
	Gap(side Side, off, n int64, ts time.Time)
	// Fin 在 side 方向 FIN 之前的字节全部交付或认定为缺口之后调用。
	Fin(side Side, ts time.Time)
	// Reset 在收到 RST 时调用。调用前，两个方向缓存的乱序数据先按缺口规则交付。
	Reset(ts time.Time)
	// Closed 是最后一个回调，此时连接已经从表里移除。
	Closed(reason CloseReason, ts time.Time)
}

type Config struct {
	ReorderTimeout  time.Duration // 乱序数据最多等多久，取 2s
	MaxReorderBytes int64         // 单方向乱序缓存的上限，取 --max-message
	IdleTimeout     time.Duration // 空闲多久释放连接，取 2 倍 --timeout
}

func NewAssembler(cfg Config, open func(ConnInfo) Handler) *Assembler
func (a *Assembler) Add(seg *decode.Segment, ts time.Time)
// Advance 处理乱序超时和空闲释放。now 单调不减。
// 为了省事，每经过 100ms 抓包时间才扫描一次全部连接即可。
func (a *Assembler) Advance(now time.Time)
// Flush 在输入结束时调用：先把每条连接的空洞都认定为缺口，再依次 Closed(CloseEOF)。
func (a *Assembler) Flush(now time.Time)
// Release 主动释放连接（内存超限时用），回调 Closed(CloseEvicted)。连接不存在时返回 false。
func (a *Assembler) Release(k Key, now time.Time) bool
func (a *Assembler) BufferedBytes() int64    // 乱序缓存里的字节数
func (a *Assembler) Len() int                // 当前的连接数
func (a *Assembler) LeastRecent() (Key, bool) // 最久没有收到包的连接
```

行为清单（1–11）：

1. 三次握手后双向发数据：`open` 收到的 `RolesKnown` 为真，`Key.A` 是客户端。两个方向的第一个字节偏移都是 0，也就是 ISN+1 那个字节。
2. 没看到 SYN、第一个包是 SYN-ACK 时，`Key.A` 取 SYN-ACK 的目的地址，`RolesKnown` 为真。
3. 第一个包是普通数据包（开始抓包前连接已经建立）时，`Key.A` 取它的源地址，`RolesKnown` 为假，这个方向的第一个字节偏移为 0。另一方向的起点取这个包的 Ack，这样 `peerAck` 从第一个包起就能换算。
4. 对于表里没有的连接，不带负载的 ACK、FIN、RST 不建连接，也不产生任何回调。
5. 重传已经交付过的数据时没有回调。部分重叠时只交付新的那部分。
6. 乱序：后面的段先到时先缓存，等前面的段到了，再按偏移顺序依次交付。
7. 缓存里的段互相重叠时，重叠部分以先到的为准。测试要构造同一区间内容不同的两个段，断言交付的是先到的内容。
8. 用 ACK 认定缺口：side 0 丢了一段，后一段已缓存，side 1 的 ACK 越过了丢掉的那段。这时要立即交付 `Gap`，再交付缓存的数据。即使没有缓存数据，只要对端 ACK 越过了下一个期望的偏移，也要立即交付 `Gap`。
9. 乱序超时：空洞一直没补上，对端也没有 ACK 越过它。`Advance` 推进到最早那个缓存段到达后第 2 秒时，先交付 `Gap`，再交付缓存数据；到达后 1.9 秒时什么都不做。
10. 单方向乱序缓存超过 `MaxReorderBytes` 时，立即认定缺口并交付。
11. `Segment.Missing` 不为 0 时，先交付 `Data(Payload)`，再交付紧跟其后的 `Gap(Missing)`。

行为清单（12–20）：

12. FIN 按序号生效：FIN 之前的字节都交付完之后，才回调 `Fin(side)`。FIN 先到、前面还有数据没到时，等数据补上，或者按第 8–10 条认定缺口之后再回调。两个方向都回调过 `Fin` 之后，回调 `Closed(CloseFin)`。
13. 收到 RST 时，依次回调：缓存数据的 `Gap` 和 `Data`、`Reset`、`Closed(CloseReset)`。不检查 RST 的序号是否落在窗口内。
14. 序号回绕：ISN 为 `0xFFFFFF00` 时，跨过 2³² 的数据偏移仍然连续。
15. 保活探测（序号等于下一个期望序号减 1，负载 0 或 1 字节）没有回调。
16. 同一四元组上出现了不带 ACK 的 SYN，而且序号和原来的 ISN 不同，或者原连接没看到过 SYN：旧连接回调 `Closed(CloseReplaced)`，再用新的 `Handler` 建立新连接。SYN 重传（序号相同）则忽略。
17. 连续 `IdleTimeout` 没有收到包的连接，在 `Advance` 里先把空洞认定为缺口，再回调 `Closed(CloseIdle)`。`Flush` 对所有连接做同样的处理，原因是 `CloseEOF`。
18. `peerAck` 的换算：服务端数据包的 Ack 等于客户端 ISN+1+N 时，`peerAck` 是 N；包没有 ACK 标志时是 -1。
19. `Release` 之后回调 `Closed(CloseEvicted)`，之后这条连接的包按第 3、4 条当新连接处理。`LeastRecent` 返回最后一个包时间最早的连接。
20. `BufferedBytes` 等于乱序缓存里的字节数，交付后减少。缓存乱序段时要拷贝负载；按序到达的段直接把 `Payload` 传给 `Data`，不拷贝。要有按序大流量的基准测试。

### L4 `internal/http1`：HTTP/1.x 增量解析

文件：`internal/http1/parser.go`（可拆成多个文件）、`parser_test.go`。一个 `Parser` 只解析一个方向的字节流。

```go
type Kind uint8

const (
	Request  Kind = iota
	Response
)

type Section uint8

const (
	SecHead     Section = iota // 起始行、头部和结尾的空行
	SecBody                    // body 的线上字节：chunk 长度行、数据、CRLF 和最后的 "0\r\n"
	SecTrailer                 // trailer 头和最后的 CRLF
	SecUnparsed                // 失步后到重新对齐之前的原始字节
)

type Head struct {
	Method, Target  string // 请求用
	Status          int    // 响应用
	Proto           string // "HTTP/1.0" 或 "HTTP/1.1"
	ContentType     string // 第一个值，去掉首尾空白；没有时为空
	ContentEncoding string
	Upgrade         bool // 请求：方法是 CONNECT，或带 Upgrade 头
	Tunnel          bool // 响应：101，或 CONNECT 的 2xx；此后这个方向不再解析
}

type Begin struct {
	Off     int64     // 起始行第一个字节的流偏移
	TS      time.Time // 这个字节所在包的时间
	PeerAck int64     // 这个字节所在包的 peerAck，原样透传
	Orphan  bool      // 失步时没有正在解析的消息，后面只会有 SecUnparsed
}
```

```go
// Sink 接收解析事件。所有 []byte 参数只在回调期间有效。
type Sink interface {
	Begin(b Begin)
	Raw(sec Section, b []byte) // 当前消息的线上字节，按顺序拼起来就是原文
	Head(h *Head)              // 头部解析完成；h 只在回调期间有效
	Body(b []byte)             // 去掉 chunked 编码后的 body 字节
	Gap(sec Section, n int64)  // 当前消息里有 n 字节没抓到
	End(complete bool, ts time.Time)
	Desync(off int64) // 在 off 处失步，用于统计
}

type Options struct {
	Resync bool // 从失步状态开始：没看到连接开头时用
	// Method 只给响应解析器用：解析完一个非 1xx 响应的头部时调用，
	// 返回对应请求的方法；不知道时返回空串，按 GET 处理。
	Method func() string
}

func NewParser(kind Kind, sink Sink, opt Options) *Parser
func (p *Parser) Feed(off int64, b []byte, peerAck int64, ts time.Time)
func (p *Parser) Gap(off, n int64, ts time.Time)
// Close 在流结束时调用。fin 为真表示正常 FIN，为假表示 RST 或输入结束。
func (p *Parser) Close(fin bool, ts time.Time)
// Resume 和 Tunnel 只对请求解析器有效，见行为 13。
```

一条消息的事件顺序是：`Begin`、若干个 `Raw`、`Body` 和 `Gap`（在头部结束时插入一次 `Head`），最后是 `End`。一条 `End` 之后才会出现下一条 `Begin`。

行为清单（1–8）：

1. 一次喂入一个 Content-Length 请求，事件依次是：`Begin(Off=0)`、`Raw(SecHead, 起始行和头部)`、`Head`、`Raw(SecBody)`、`Body`、`End(true)`。把同一请求一个字节一个字节地喂入，拼出的 Raw 内容和事件类型序列都相同。
2. 只有起始行完整且合法之后才 `Begin`。请求行是 `方法 SP 目标 SP HTTP/1.0|1.1`，方法是 1 到 20 个大写字母或 `-`。状态行是 `HTTP/1.x SP 三位数字`，后面跟 ` 原因短语` 或直接换行。行尾是 CRLF 或 LF 都接受。请求行之前的空行跳过。
3. chunked：`Raw(SecBody)` 包含长度行（可以带 `;扩展`）、数据、CRLF 和 `0\r\n`；`Body` 只有数据；trailer 以 `SecTrailer` 交付。chunked 和 Content-Length 同时出现时，按 chunked 处理。
4. body 长度的判定：
   - 请求：chunked、Content-Length，两者都没有时为 0。
   - 响应：1xx、204、304，以及 `Method()` 返回 HEAD 时，没有 body；否则看 chunked 和 Content-Length，两者都没有时读到 `Close` 为止。
   - 响应的 Transfer-Encoding 最后一项不是 chunked 时，也读到关闭为止。
5. 1xx（101 除外）是独立的一条消息，结束后继续解析下一个响应。
6. 响应是 101，或者 `Method()` 返回 CONNECT 且状态码是 2xx 时，`Head.Tunnel` 为真。这条消息 `End(true)` 之后，这个方向的字节不再产生任何事件。
7. 读到关闭为止的 body 在 `Close(fin=true)` 时 `End(true)`，`Close(false)` 时 `End(false)`。其他消息如果在中途关闭，一律 `End(false)`。
8. 下面的缺口不影响解析，交付 `Gap(SecBody, n)` 后继续：落在 Content-Length body 里、chunk 数据里，或读到关闭为止的 body 里。缺口正好补齐 Content-Length 时，照常 `End(true)`（完整性由引擎判断）。

行为清单（9–15）：

9. 以下情况会失步：缺口落在起始行、头部、chunk 长度行或 trailer 里；缺口越过了 body 的结尾；格式不合法（起始行不对、头部行没有冒号、Content-Length 不是数字、请求的 Transfer-Encoding 不是 chunked）；头部超过 64 KiB；chunk 长度行超过 4 KiB；两条消息之间（等起始行时）出现缺口，这段缺口里可能有一整条消息没抓到。失步时先交付 `Desync(off)`，再进入扫描状态。
10. 扫描状态：只在行首找合法的起始行。行首指 `\n` 之后、缺口之后的第一个字节，或者一次 `Feed` 的第一个字节（调用方按 TCP 段喂入，就是段的开头；失步前的字节常常不以换行结尾，下一个消息通常从新的段开始）。已经缓存着跨 `Feed` 的起始行候选时接着读它。因此扫描状态下切分方式会影响对齐，切分不变性只对不进入扫描状态的流成立。扫描期间的字节归属如下：
    - 失步前有正在解析的消息：这些字节以 `Raw(SecUnparsed)` 交付给它。
    - 没有正在解析的消息：先 `Begin(Orphan=true)`，再交付 `Raw(SecUnparsed)` 和 `Gap(SecUnparsed, n)`。没有任何字节和缺口时，不产生 Orphan 消息。
    - 找到起始行时，先 `End(false)` 结束上面的消息，再 `Begin` 新消息。
11. `Options.Resync` 为真时，从扫描状态开始，行为同第 10 条。例如从一个响应的 body 中间开始喂入，第一个状态行之前的字节就是 Orphan 消息。
12. 扫描中遇到超过 8 KiB 还没换行的行，不当作起始行候选，但字节仍按第 10 条交付。
13. 请求的 `Head.Upgrade` 为真时，这个请求 `End` 之后，后面喂入的字节先缓存起来，不解析，最多缓存 64 KiB，超出的部分丢弃。之后：
    - 调用 `Resume()`：把缓存的字节按 HTTP 解析。
    - 调用 `Tunnel()`：丢弃缓存，此后不再产生事件。
14. 头部名不区分大小写。重复的 Content-Length 取值相同时接受，取值不同时失步。
15. 性能：Content-Length body 的大段数据直接切片交付，不逐字节处理。1 MiB body 按 1460 字节分片喂入的基准测试要达到 1 GB/s 以上。

### E1 交互组装（能看到握手的连接）

1. 请求 GET，响应 200，带 Content-Length，关键词只出现在响应 body 里。输出一块，状态 `complete`。定位行的时间是请求第一个包的时间；耗时是响应最后一个包的时间减去请求最后一个包的时间。
2. 没有命中时不输出。此时 `Stats.Exchanges` 为 1，`Matched` 为 0。
3. 关键词只出现在请求头里，也要输出。
4. 同一连接上的 3 个 keep-alive 交互，只有第 2 个命中，就只输出第 2 个。
5. 管道化：连发两个请求之后，才依次收到两个响应。两个请求都命中时，两块的请求和响应要配对正确。
6. chunked 响应，关键词被拆在两个 chunk 里，要能命中。输出里保留 chunk 长度行。关键词只出现在 chunk 长度行里时不算命中，例如关键词是 `a3f`，chunk 长度行是 `a3f`，数据里没有 `a3f`。
7. 关键词被拆在两个 TCP 段里，也要能命中。
8. 100 Continue 之后再 200：输出一块，块里依次是请求、100 响应、200 响应。
9. HEAD 请求的响应带 `Content-Length: 1000` 但没有 body。之后同一连接上的下一个交互照常解析。
10. 两条连接交错传输：后开始但先结束的交互先输出。
11. 响应 body 里含 NUL：输出占位行，关键词在 body 里时带 `matched`。响应带 `Content-Encoding: gzip`：也输出占位行，行里带上 gzip。
12. 读到关闭为止的响应，服务端 FIN 之后状态是 `complete`。
13. 服务端先 FIN，或者发 RST，之后才轮到的请求：`no-response(closed)`。响应收到一半时来了 RST：`incomplete`。同一四元组上出现新连接（`CloseReplaced`）时，旧连接的在途交互按同样规则处理。
14. 只有客户端发了 FIN，之后服务端才回响应：状态是 `complete`。
15. 101 升级响应之后：交互状态是 `complete`。之后连接上即使出现关键词，也不再输出任何块。CONNECT 加 200 的情况相同。带 Upgrade 头的请求得到 400 响应，或者超时了，都调用 `Resume()`，同一连接上的下一个请求照常解析。
16. 调用 `Finish` 时：只有请求没有响应的交互是 `no-response(eof)`；响应收到一半的是 `incomplete`。

### E2 半路连接、丢包和配对校验

1. 没看到 SYN 的连接，第一个包是客户端的请求：角色判定正确，交互照常输出。实现方式是：角色未知的每个方向同时挂一个请求解析器和一个响应解析器，都用 `Resync` 模式；哪个先产生非 Orphan 的 `Begin`，就按它确定角色，另一个丢弃。
2. 没看到 SYN，第一个包是某个响应 body 的中间部分：这些字节丢弃，计入 `Orphans`。之后的请求和响应照常配对。
3. 没看到 SYN，第一个完整的消息是响应，之前的请求没抓到：输出一块，状态是 `no-request`，定位行时间用响应第一个包的时间。
4. ACK 校验：请求 R 在队列里，但下一个响应的 `Begin.PeerAck` 不大于 R 的起始偏移（服务端当时还没收到 R）。这个响应作为 `no-request` 交互，R 继续等自己的响应。Orphan 消息也做这个校验（`PeerAck` 为 -1 时跳过），校验不通过就丢弃，计入 `Orphans`。
5. 客户端请求 body（Content-Length）里有缺口：输出里有 `[gap: N bytes missing]`，状态是 `incomplete`，其他部分照常匹配。
6. 客户端请求头里有缺口：失步。已经看到请求行的请求，把到下一个请求行之前的字节以 Unparsed 形式收下来，状态是 `incomplete`。下一个请求正常。
7. 服务端响应头里有缺口：失步。Unparsed 字节归入队首请求的响应，这个交互 `incomplete`，重新对齐时结束。下一个响应和下一个请求配对。
8. 服务端丢了一整个响应（缺口正好落在两个响应之间）：这段缺口作为 Orphan 归入队首请求的响应，这个交互 `incomplete`；下一个响应和下一个请求配对，不会错位。
9. 客户端方向的 Orphan 消息丢弃，只计数。比如一条 TLS 连接：它不输出任何块，内存计量也不随它的数据量增长。
10. 回放两份内容相同的抓包，一份每个包都完整，另一份把某些段重传一次，还把相邻两段顺序颠倒：两份的输出逐字节相同。

### E3 超时和迟到响应

1. 请求发完后一直没有响应：`Advance` 到 +29.9 秒时不输出；到 +30 秒时输出一块，状态 `no-response(timeout)`。
2. 响应收到一部分之后没了下文：从最后一次收到数据起 30 秒，状态 `incomplete`。
3. 同一连接上管道化的请求 R1（t=0）和 R2（t=1）都没有得到响应。R1 在 t=30 超时；R2 从 t=30 轮到队首时才开始计时，在 t=60 超时，t=59.9 时还没有超时。
4. 迟到响应：R1 超时后，它的响应在 t=35 才到。不输出第二块，`Late` 加 1，也不缓存它的数据。之后同一连接上的请求 R2 和它自己的响应配对，输出正确。
5. 在 `Advance` 里到期的交互按到期时间的先后输出。1 万个在途交互时，`Advance` 的耗时和到期的数量成正比，和在途交互总数无关。用最小堆或时间轮实现，要有基准测试。
6. 空闲 60 秒的连接被释放：`Stats` 里连接数随之减少。之后同一四元组上的新数据按半路连接处理。

### E4 内存上限

1. `MaxMessage` 为 4 KiB，响应有 10 KiB：只缓存和匹配前 4 KiB，输出末尾有 `[truncated: 6144 bytes over --max-message]`，`Truncated` 加 1。关键词只出现在 4 KiB 之后时不算命中。
2. 计入 `MaxMemory` 的有：缓存的消息字节、`Assembler.BufferedBytes()`、每条连接 1 KiB 的固定开销、每个在途交互 512 字节的固定开销。
3. 超过上限时，从开始时间最早的在途交互起逐个丢弃，直到不超限：
   - 丢弃的交互即使已经命中也不输出。它在队列里留一个占位，之后的数据不再缓存。
   - `Evicted` 加 1；已经命中的，`EvictedMatched` 也加 1。
4. 在途交互都丢完了仍然超限：用 `Assembler.Release` 释放 `LeastRecent` 返回的连接，直到不超限。
5. `Warn` 按抓包时钟最多每 10 秒调用一次，内容是 `dropped N in-flight exchanges (M matched) to stay under --max-memory`。其中 N 和 M 是距上一次告警以来的累计数。调用 `Finish` 时，如果还有没报告过的累计数，再调用一次。
6. 在测试里把 `MaxMemory` 设为 64 KiB，构造 100 个大请求并发的场景，每个包之后记下内存计量值，它不超过上限加一个包的大小。`PeakBuffered` 和手算的值一致。
7. 基准测试：合成 1 万个交互，body 在 1–30 KB 之间，不含命中。引擎每秒处理的字节数（从 `Segment` 算起，不含 pcap 读取）不低于 150 MB/s（本机单核）。

## 7. 阶段三：`internal/run` 和 `cmd/httpgrep`（依次做 R1、R2）

### R1 `internal/run`：读入、时钟和多核分发

文件：`internal/run/run.go`、`shard.go`、`run_test.go`。

```go
type Config struct {
	Input  io.Reader
	Pipe   bool          // 输入不是普通文件；为真时启用真实时间兜底
	Stop   <-chan struct{} // 第一次收到信号时关闭
	Stdout io.Writer
	Stderr io.Writer      // 告警写到这里
	TTY    bool
	Opts   cli.Options
}

// Run 处理整个输入。matched 为真表示至少输出了一块。
func Run(cfg Config) (matched bool, st engine.Stats, err error)
```

行为清单（1–4）：

1. 用一个读取协程读 pcap，把包拷贝到可复用的批量缓冲区（例如 256 KiB 一批）后交给主循环，不要每个包一次 channel 发送。
2. 时钟取所有包时间戳的最大值。每批包处理完调用一次 `Advance`。
3. `Pipe` 为真时，主循环每 200ms 检查一次。超过 1 秒没有新包时，时钟改为：最后一个包的时间戳加上从收到它起经过的真实时间（取它和原时钟中较大的值），然后 `Advance`。测试用 `io.Pipe`：只写一个请求，保持管道不关，`--timeout 2s`，约 3 秒内应当输出 `no-response(timeout)`。
4. `Stop` 关闭后，最多再读 1 秒，或者读到输入结束为止，然后 `Finish`。读取协程可能卡在阻塞的 read 上，此时不等它，直接收尾。

行为清单（5–9）：

5. `CPUs` 大于 1 时，开 N 个分片协程，每个分片有自己的 Engine，内存上限是 `MaxMemory/N`。解码在主循环里做。按不区分方向的连接键（两个端点排序后再哈希）分到分片，同一连接总是落到同一分片。时钟推进要广播给所有分片。所有分片共用一个带互斥锁的 `output.Writer`。
6. 测试：同一份含 200 个命中交互、交错在 50 条连接上的抓包，`CPUs=1` 和 `CPUs=4` 输出的块集合相同（按块排序后比较）。
7. 错误处理：
   - 链路层类型不支持：返回错误 `unsupported link type N`。
   - pcap 头部错误：原样返回 `pcap.ErrPcapNG`、`pcap.ErrNotPcap`、`pcap.ErrEmpty`。
   - 输出写入失败：返回错误。
8. 统计：Packets、Bytes 统计所有记录（Bytes 按 caplen 累加），NotTCP、Fragments、Malformed 按 `decode.Result` 计数。结果中合并各分片的统计。
9. 设置 `debug.SetMemoryLimit`（1.5×MaxMemory）和 `runtime.GOMAXPROCS`（CPUs）的职责放在 cmd，不放在 run，以免测试互相影响。

### R2 `cmd/httpgrep`：可执行文件

文件：`cmd/httpgrep/main.go`、`tty_linux.go`、`tty_darwin.go`、`main_test.go`。

1. 流程：`cli.Parse` → 处理 help 和 version → 打开输入 → 用 `Stat` 判断输入是不是普通文件 → 检测标准输出是不是终端（用 `syscall` 的 ioctl：Linux 用 `TCGETS`，macOS 用 `TIOCGETA`）→ 设置 `GOMAXPROCS` 和内存软上限 → 注册信号 → `run.Run` → 按需打印统计 → 退出。
2. 退出码：有命中返回 0，没有命中返回 1，出错返回 2。出错信息写到 stderr，格式是 `httpgrep: <错误>`。参数错误时，再多写一行 `Try 'httpgrep --help' for more information.`。
3. 信号：第一次 SIGINT 或 SIGTERM 时关闭 `Stop`。第二次 SIGINT 时立即 `os.Exit(130)`。SIGPIPE 保持 Go 的默认行为。
4. `--version` 输出 `httpgrep <版本>`。版本号用 `-ldflags "-X main.version=..."` 注入，默认是 `dev`；再附上 `runtime/debug.ReadBuildInfo` 里的 vcs.revision（有的话）。
5. `--stats` 按设计文档第 11 节写到 stderr，每行一项，标签用英文，例如 `throughput: 123.4 MB/s`。
6. 黑盒测试：`TestMain` 用 `go build` 编译到临时目录。设置了环境变量 `HTTPGREP_BIN` 时，改用它指向的程序（阶段四用它在容器里跑）。输入用 pcapgen 生成，覆盖以下场景：
   - 退出码 0、1、2；
   - 读文件、读标准输入、文件参数写成 `-`；
   - pcapng 输入、空输入、非 pcap 输入的出错信息；
   - `-e` 写多次，以及 `-E`；
   - `--stats` 的各项都出现在 stderr；
   - 用 `io.Pipe` 验证真实时间兜底；
   - 发一次 SIGINT：在途交互以 `no-response(eof)` 输出，退出码 0；发两次 SIGINT：退出码 130。
7. 终端检测：对管道和 `/dev/null` 都返回假。输出到文件时逐字节不转义。

## 8. 阶段四：验证（4 条只读通道并行，之后一个修复者）

验证通道不改产品代码。脚本放在 `scripts/` 下，各通道只改自己负责的脚本。报告里不许出现抓包里的 body 内容、头部取值和 URL 参数，只能写计数、`tcp.stream` 编号、客户端端口、时间、状态和 sha256。

- **V1 真实样本**（`scripts/compare-tshark.sh`，或者 `tools/samplecheck` 下的 Go 程序）：
  - 样本用 `find ~/Downloads ~/Documents/反馈处理 -name '*.pcap'` 找到。至少覆盖 111、222、34095128、490419C6117A0087747906 这四份以太网抓包，以及一份 SLL2 抓包。
  - 关键词 `490419C6117A0087747906`：在同名文件里至少命中一次。关键词 `34095128`：在所有文件里都不命中。
  - 空关键词会输出所有交互，用它和 tshark 核对以下三组计数：`complete` 的数量对应 tshark 里带 `http.response_in` 的请求数；`no-response` 的数量对应没有 `http.response_in` 的请求数；`no-request` 的数量对应没有 `http.request_in` 的响应数。
  - 差异按类别各举至多 5 个例子，写出原因。
  - 记录 `--stats` 的输出，以及 `/usr/bin/time -l` 测得的最大 RSS。
- **V2 实时抓包**（`scripts/live-lo0.sh`）：
  - 在 127.0.0.1 的随机端口起本地 HTTP 服务，要有一个会睡 10 秒的接口。然后运行 `tcpdump -i lo0 -U -w - port P | httpgrep --timeout 3s 关键词`，用 `curl -s -o /dev/null` 发请求。
  - 验证：命中的块在响应完成后 1 秒内输出；慢接口约 3 秒后输出 `no-response(timeout)`；向进程组发一次 SIGINT 后，在途交互以 eof 状态输出，进程正常退出。

- **V3 Linux 容器**（`scripts/linux-check.sh`）：
  - 用 `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o dist/httpgrep-linux-amd64 ./cmd/httpgrep` 编译，用 `file` 确认是静态链接。
  - 设置 `HTTPGREP_BIN` 指向包装脚本，脚本执行 `docker run --rm -i --platform linux/amd64` 加上 busybox:1.37，并把 `$TMPDIR` 挂载到容器里的同一路径。用它跑 `cmd/httpgrep` 的黑盒测试。信号类用例在容器里不稳定的，可以标记跳过并说明原因。
  - 各包测试用 `GOOS=linux GOARCH=arm64 go test -c` 编译，再放到 `ubuntu:24.04`（arm64）容器里运行。
  - 用同一份真实样本、`TZ=UTC`，比较 amd64 容器里和本机的输出，sha256 必须相同。
- **V4 性能**：
  - 运行全部基准测试。
  - 用 `httpgrep --stats --cpus 1 关键词 111.pcap > /dev/null` 连跑 3 次，记下吞吐和 RSS；再用 `--cpus 4` 跑一次。
  - 本机单核低于 100 MB/s 时（用来近似 x64 上的 50 MB/s），用基准测试的 `-cpuprofile` 找出前 10 个热点，并给出优化建议。

修复者拿到四份报告后，按 TDD 修复：先在对应接缝上写一个能复现问题的失败测试，再修复。修完只重跑失败过的验证项。这样的循环最多两轮，之后仍然存在的问题写进最终报告。

## 9. 阶段五：整体评审

两个评审者并行，都只读：

- 规格评审：逐节对照设计文档，列出没实现的、实现得不一样的，以及实现了但文档里没有的。
- 健壮性评审：检查 panic、内存有没有上限、并发和竞态，并给 pcap、decode、tcp、http1 各跑 60 秒 fuzz。fuzz 目标由评审者新增到 `*_fuzz_test.go`，这是它唯一允许写入的地方。

然后由一个修复者处理阻断和重要问题，处理方式同阶段四。最后父会话自己运行完整门禁：`gofmt -l .`、`go vet ./...`、`go test -race ./...`，交叉编译 linux/amd64，再用 V1 的关键词抽查一次，确认全部通过后向用户汇报。
