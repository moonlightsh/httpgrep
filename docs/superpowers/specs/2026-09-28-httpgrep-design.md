# httpgrep 设计：从实时抓包中检索 HTTP 交互

状态：已确认
日期：2026-09-28
依据：三轮需求澄清（对话确认）。术语见 `CONTEXT.md`，架构决策见 `docs/adr/`。

## 1. 目标与范围

在生产服务器上边抓包边检索，把请求或响应里含有关键词的 HTTP 交互完整打印出来：

```sh
tcpdump -i lo -U -w - port 7010 | httpgrep 490419C6117A0087747906
```

- 运行环境：Linux x86_64，内核不低于 3.2（CentOS 7 及以上）。交付物是一个静态单文件，服务器上除了 tcpdump 不用装任何东西。
- 实时检索时 tcpdump 要加 `-U`，否则它攒满缓冲区才往管道里写。
- 流量规模（两份真实抓包实测）：平均 1,100–1,800 QPS，峰值约 2,500；在途交互峰值约 600 个，同时存活的连接峰值约 850 条；响应 p99 约 34KB，最大 2.3MB；慢响应集中在 19–21.5 秒。
- v1 不做：HTTPS、HTTP/2（含 h2c）、WebSocket 消息、body 解压（往后放）、pcapng、多文件输入、索引（ADR-0001）、IP 分片重组，以及 grep 的其他选项（-i -v -w -x -c -m -q -o -a -f -P、上下文、多文件相关选项等）。

## 2. 用法

```sh
httpgrep [选项] 关键词 [文件]
httpgrep [选项] -e 关键词 [-e 关键词]... [文件]
```

不给文件或文件是 `-` 时读标准输入。最多一个文件；用了 `-e` 时，剩下的参数是文件。

| 选项 | 默认 | 说明 |
|---|---|---|
| `-e 关键词` | 无 | 指定关键词，可以写多次，命中任意一个就算命中 |
| `-E` | 关 | 所有关键词按正则处理 |
| `--timeout 时长` | `30s` | 交互超时 |
| `--max-memory 大小` | `256M` | 缓存数据的总上限 |
| `--max-message 大小` | `8M` | 单个请求或响应的缓存上限 |
| `--cpus N` | `1` | 使用的 CPU 核数 |
| `--stats` | 关 | 退出前把统计打印到 stderr |

- 大小可以带 K、M、G 后缀（按 1024 进位）；时长写成 `30s`、`2m` 这样。
- 选项放在关键词和文件的前面或后面都行；`--` 之后的参数一律不当选项。
- 另有 `--help` 和 `--version`。工具输出的文字（状态词、提示、帮助）都用英文。
- 退出码同 grep：有命中返回 0，没有命中返回 1，出错返回 2（参数错误、输入为空或不是 pcap、读写失败等）。

## 3. 输入

- 格式：pcap，微秒和纳秒两种时间精度、两种字节序都支持。输入是 pcapng 时报错，提示改用 `tcpdump -w`。末尾不完整的包（tcpdump 被强行终止时常见）按输入结束处理。
- 链路层：Ethernet，含 VLAN 标签（`tcpdump -i lo` 和物理网卡）；Linux cooked v1、v2（`-i any`）；Raw IP；BSD/macOS 回环（本机测试用）。
- 网络层：IPv4、IPv6。IP 分片跳过并计数。不校验校验和，回环抓包的校验和常常不对。
- 包被 snaplen 截断（抓到的长度小于原始长度）时，没抓到的部分按缺口处理。
- 按端口、主机过滤交给 tcpdump 的过滤表达式。

## 4. TCP 重组

- 按四元组区分连接。看到 SYN 的连接，发 SYN 的一方是客户端；没看到 SYN 的连接（开始抓包前已建立）按内容判断，发出请求行的一方是客户端，发出状态行的一方是服务端。
- 两个方向分别按序号重组成字节流：重传和重复的数据丢弃，重叠部分以先到的为准，乱序数据先缓存，等前面的补上。
- 认定缺口的时机：对端 ACK 已经越过没抓到的数据时立即认定（数据送达了，只是没抓到）；否则在乱序数据超过 `--max-message`、等了 2 秒还没补上，或者连接关闭时认定。认定后跳过缺口继续处理，所在交互标为不完整。
- 同一四元组上出现序号不同的新 SYN 时，旧连接结束，按新连接处理。
- FIN 按序号生效：它之前的数据都到齐或认定缺口后，这个方向才算结束；RST 立即生效。双方都 FIN 或任一方 RST 后释放连接；连续 2 倍交互超时（默认 60 秒）没有任何包的连接也释放，这样释放时还在途的交互按超时结束（no-response(timeout) 或 incomplete），排在队列后面、还没开始计时的请求也一样。

## 5. HTTP/1.x 解析与配对

- 客户端方向依次解析请求，服务端方向依次解析响应。只认 HTTP/1.0 和 HTTP/1.1，行尾是 `\r\n` 或 `\n` 都接受。
- body 长度按 RFC 9112 判断。请求：chunked 或 Content-Length，都没有就没有 body。响应：HEAD 请求的响应、1xx、204、304 没有 body；其余看 chunked 或 Content-Length，都没有就读到服务端关闭连接为止。
- 1xx 中间响应归入所属交互，最终响应之前可以有多个。101 升级响应和 CONNECT 的 2xx 响应之后，这条连接不再按 HTTP 解析，也不再缓存数据。
- 配对：同一连接上，响应按请求的顺序配对。另用响应所带的 ACK 校验：如果响应的 ACK 表明服务端当时还没收到这个请求的第一个字节，这个响应就不属于它，按缺请求处理，请求继续等。
- 连接关闭：服务端 FIN 或任一方 RST 之后，在途交互随之结束，没收到响应的标 no-response(closed)，响应没收完的标 incomplete；读到关闭为止的响应，在服务端 FIN 时算收完。只有客户端 FIN 时照常等服务端，它还可能回响应。
- 交互超时后在原位置留一个占位，保证后面的响应配对正确。它的迟到响应只解析长度、不缓存，不参与匹配也不输出，只计数。

## 6. 丢包与失步

- 缺口落在长度已知的 body 里（按 Content-Length，或在 chunk 数据内部）：插入缺口标记，跳过缺口继续解析。
- 缺口落在起始行、头部或 chunk 长度行里，或者数据不符合 HTTP 格式：这个方向失步，在后面的数据里找下一个请求行（服务端方向找状态行）重新对齐。对齐之前抓到的字节按原始字节匹配、原样输出，归属如下：
  - 客户端方向：归入正在解析的请求；连请求行都没抓到的，直接丢弃。
  - 服务端方向：归入正在解析的响应；没有正在解析的响应时，归入排在最前面的请求的响应。这个交互标为不完整，重新对齐时结束，之后的响应和之后的请求配对。
  - 不属于任何交互的（例如开始抓包时截在半路的数据）直接丢弃。
- 头部超过 64KB 还没结束，按不符合 HTTP 格式处理。非 HTTP 的连接（比如 TLS）找不到起始行，数据只扫描、不缓存。

## 7. 匹配

- 默认按字面匹配，区分大小写（grep 默认是基本正则，这里不同）。加 `-E` 时所有关键词按 Go 的正则语法（RE2）解释，可以用 `|`、`+`、`{n}`、`\d`、`(?i)` 等，不支持反向引用。
- 关键词里的换行把它拆成多个关键词；空关键词匹配所有交互。这两点同 grep。
- 和 grep 一样逐行匹配：按 `\n` 分行，行尾的 `\r` 不算行内容。`^`、`$` 锚定行首和行尾，一次匹配不跨行。
- 参与匹配的内容：请求和响应（含 1xx）的起始行、头部、chunked 的 trailer，以及去掉 chunked 编码后的 body，所以跨 TCP 包、跨 chunk 都能命中。定位行不参与匹配。
- 二进制 body（见第 9 节）照样参与匹配。v1 不解压，带 Content-Encoding 的 body 按压缩后的字节匹配，基本搜不到。
- 不参与匹配：超过 `--max-message` 的部分、迟到响应。

## 8. 超时、内存和 CPU

- 时钟：用抓包时间戳计时，回放抓包文件和实时抓包的超时判定一致。输入不是普通文件（管道、FIFO）时，如果超过 1 秒没有新包，时钟从最后一个包的时间戳起按真实经过的时间往前推，免得流量停下来后，命中的交互迟迟不输出。时钟不倒退。
- 交互超时：从交互最后一次收到数据（请求或响应的都算）起计时，连续 `--timeout` 没有新数据就结束。没收到响应的标 no-response(timeout)，响应只收到一部分的标 incomplete。同一连接上排队等响应的请求，轮到它时才开始计时。
- 内存：计入 `--max-memory` 的是缓存的请求和响应数据、乱序数据，以及每条连接、每个在途交互、每个占位的固定开销。超限时从最早开始的在途交互起逐个丢弃，直到不超限；在途交互不够丢，就释放最久没有数据的连接。丢弃的交互像超时的一样留占位，后续数据不再缓存；即使已经命中也不输出，只计数并在 stderr 警告，警告里写明其中有几个已命中。下面几项不计入，各有自己的上限：`-E` 模式下正则的行缓存（每个扫描器最多 8 MiB，只有超长行才会用到），解析器内部的缓存（带 Upgrade 头的请求之后缓存的字节，每条连接最多 64 KiB；失步扫描时的行缓存，每个方向最多 8 KiB）。所以进程的实际内存会高于计量值，`-E` 遇到超长行时尤其如此。
- 单个请求或响应超过 `--max-message` 的部分不缓存。
- Go 运行时的软内存上限设为 `--max-memory` 的 1.5 倍。按现有流量估算，进程平时只占几十 MB。
- CPU：默认只用 1 个核（GOMAXPROCS=1）。`--cpus N` 时按连接把包分给 N 个工作协程，内存上限平均分给各协程。

## 9. 输出

交互结束（响应收完、超时、连接关闭或输入结束）后整块输出，每块输出完立即刷新。输出按交互结束的先后排列，不按请求发出的先后。块与块之间用一行 `--` 分隔（同 grep）。样例（内容是编的）：

```text
2026-09-28 15:30:12.345 127.0.0.1:52814 -> 127.0.0.1:7010 complete 12.0ms
POST /api/device/bind HTTP/1.1
Host: 127.0.0.1:7010
Content-Type: application/json
Content-Length: 38

{"sn":"490419C6117A0087747906","ch":1}
HTTP/1.1 200 OK
Content-Type: application/json
Transfer-Encoding: chunked

15
{"code":0,"msg":"ok"}
0

--
2026-09-28 15:30:13.020 127.0.0.1:52990 -> 127.0.0.1:7010 no-response(timeout)
GET /api/device/status?sn=490419C6117A0087747906 HTTP/1.1
Host: 127.0.0.1:7010

```

定位行（每块第一行）：

- 时间：请求第一个包的抓包时间，缺请求时用响应的。按本机时区，精确到毫秒。
- 地址：客户端 -> 服务端。IPv6 写成 `[::1]:52814`。
- 状态：没有任何异常时写 `complete`。否则按 `no-request`、`incomplete`、`no-response(原因)` 的顺序，把出现的项用逗号连接。原因是 `timeout`（交互超时）、`closed`（连接关闭）、`eof`（输入结束）。
- 耗时：从请求发完到响应收完，一律以毫秒为单位、保留一位小数，方便用 awk 筛选。请求和响应都有时才输出。

内容：请求、1xx 中间响应、最终响应依次原样输出，chunked 的长度行也保留。某一部分末尾没有换行时补一个。除此之外，只会出现下面三种由 httpgrep 插入的行：

- 缺口：`[gap: 1460 bytes missing]`
- 截断：`[truncated: 1048576 bytes over --max-message]`
- 二进制 body 占位：`[binary body omitted: application/x-protobuf, 12.3 KB, matched]`；带 Content-Encoding 时写成 `[binary body omitted: gzip, application/json, 3.4 KB]`，没有 Content-Type 时省略这一项。body 里有命中时才带 `matched`。

二进制 body 的判断：去掉 chunked 编码后，body 里有 `\t` `\r` `\n` 以外的 C0 控制字符（0x00–0x1F，含 NUL）或 DEL（0x7F），或者带 Content-Encoding。整个 body（包括 chunk 长度行和其中的缺口标记）换成占位行。GBK 等非 UTF-8 文本不含这些字符，不算二进制，原样输出。

输出到终端时，C0 控制字符（`\t` `\r` `\n` 除外）、DEL 和 C1 控制字符转成 `\x1b` 这样的可见形式；命中的文字标红，定位行和 `--` 也用颜色区分。输出到文件或管道时不转义、不加颜色，一个字节都不改。

除了出错信息和 `--stats`，stderr 只在因内存上限丢弃交互时输出警告，同类警告至少间隔 10 秒（按抓包时钟），警告里的个数是距上一次警告以来的累计数，输入结束时还有没报告的再补一行。`--cpus N` 时各协程的丢弃合在一起计数、统一限频。

## 10. 信号与退出

- 第一次 Ctrl-C 或 SIGTERM：先把管道里已经写入的数据读完（最多 1 秒；和 tcpdump 一起按 Ctrl-C 时，tcpdump 退出前写出的最后一批包也能处理到），再结束所有在途交互（状态 no-response(eof) 或 incomplete），输出其中命中的，加了 `--stats` 时打印统计，最后按有没有命中返回 0 或 1。
- 第二次 Ctrl-C：立即退出，退出码 130。
- 标准输出被关闭（比如接了 `| head`）时直接退出，和 grep 一样由 SIGPIPE 终止。

## 11. 统计（--stats）

退出前打印到 stderr：处理的包数和字节数、抓包时长、处理耗时和吞吐（MB/s）；连接数，其中没看到 SYN 的有多少；交互数、命中数、各状态的个数；迟到响应、因内存丢弃、被截断的个数；缺口的个数和字节数、失步次数、跳过的 IP 分片数；缓存数据、在途交互、连接数的峰值。

## 12. 实现要点

- 只用 Go 标准库，不引入第三方依赖。pcap 读取、从链路层到 TCP 的解码、TCP 重组都自己实现（ADR-0002）。TCP 重组不用 gopacket：这里要按字节把缓存计入内存上限，还要用对端 ACK 立即认定缺口；gopacket 按页计缓存，缺口要等定时刷新或缓存超限才跳过。
- 用 Go 1.27 编译：`CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath ./cmd/httpgrep`。
- 包划分：
  - `cmd/httpgrep`：入口、信号、退出码
  - `internal/cli`：解析命令行参数
  - `internal/run`：读入循环、时钟、多核分发
  - `internal/pcap`：读 pcap 数据流
  - `internal/decode`：链路层、IP、TCP 头解码
  - `internal/tcp`：连接表、TCP 重组、缺口认定
  - `internal/http1`：HTTP/1.x 增量解析、去 chunked、失步后重新对齐
  - `internal/match`：字面和正则的逐行匹配
  - `internal/engine`：交互配对、生命周期管理、超时、内存计量
  - `internal/output`：输出块渲染、终端转义和高亮
  - `internal/pcapgen`：生成测试用的抓包，只在测试里使用

## 13. 验证

- 本机（macOS arm64）做功能验证：
  - 单元测试覆盖各层，测试用的抓包由测试代码生成，不依赖真实数据。
  - 端到端：回放真实样本（`~/Downloads` 下的抓包，含生产数据，不进仓库），命中结果和 tshark 交叉核对。
  - 模拟实时：按抓包时间戳限速把 pcap 写进管道，验证超时、逐块输出和 Ctrl-C。
  - 实时抓包：当前用户在 access_bpf 组里，不用 sudo 就能执行 `tcpdump -i lo0 -U -w - port 端口 | httpgrep 关键词`，配合本地 HTTP 服务测试。
  - Linux：交叉编译出 linux/amd64 静态版本，在本机 Docker 的 linux/amd64 容器里跑端到端用例（转译执行，只看功能）；单元测试另外编译成 linux/arm64，在原生 Linux 容器里再跑一遍。
- 性能验收由用户在 x64 Linux 上另行安排，目标是单核持续处理 50MB/s（约 2 万 QPS），指默认的字面匹配；`-E` 的吞吐取决于表达式，不在验收范围内。`--stats` 里的吞吐可以直接用来判断。
